# 医疗器械注册知识库多用户数据隔离设计报告

## 1. 报告结论

医疗器械注册知识库系统建议采用 **逻辑隔离为主、物理隔离为辅** 的多用户数据隔离方案。

系统不建议为每个用户单独部署一套数据库和 RAGFlow 服务。更合理的方式是在统一平台内，通过用户身份、工作区、数据可见性、RAGFlow Dataset 映射、MySQL 行级权限和后端统一鉴权，实现公共知识、工作区知识和用户私有知识的隔离。

核心原则如下：

1. 公共法规资料所有授权用户可检索。
2. 企业或团队资料按工作区隔离。
3. 用户上传的私有资料按用户隔离。
4. 前端不能直接指定数据库表、文件路径或 RAGFlow dataset_id。
5. 后端必须根据登录身份计算用户可访问的数据范围。
6. RAGFlow、MySQL、对象存储和审计日志均不得绕过权限系统直接访问。

最终形成：

```text
用户身份
  -> 后端权限计算
  -> 可访问 dataset 列表
  -> 可访问 documents 范围
  -> 可访问结构化表格范围
  -> 智能体检索和回答
```

## 2. 隔离目标

多用户隔离要解决四类问题：

1. **公共资料共享**  
   国家药监局、CMDE、公开指导原则、审评报告、共性问题等资料应作为公共知识库统一维护，避免重复入库。

2. **企业资料隔离**  
   不同企业、不同注册团队、不同项目组之间的内部 SOP、申报模板、历史补正问题和项目资料不能互相可见。

3. **个人资料隔离**  
   用户个人上传的临时分析文件、项目附件、未公开资料，只能被上传者本人访问。

4. **引用和审计可追溯**  
   每一次回答都需要知道引用了哪个文档、哪个 dataset、哪个表格行，以及该用户当时是否有权限访问。

## 3. 隔离模型

系统建议采用三层可见性模型：

```text
public     公共数据
workspace  工作区数据
private    用户私有数据
```

### 3.1 公共数据

公共数据包括：

1. 指导原则文本库。
2. 审评报告。
3. 共性问题和交流园地。
4. 临床评价路径推荐。
5. 征求意见稿。
6. 医疗器械批准注册产品公告。
7. 批件发布和公开监管公告。

这些数据可以被所有具备系统访问权限的用户检索，但仍需要保留来源、URL、发布日期和版本状态。

### 3.2 工作区数据

工作区数据包括：

1. 公司内部 SOP。
2. 注册申报模板。
3. 历史补正问题。
4. 内部培训资料。
5. 工作区共享项目资料。

同一工作区内的成员可以共享这些资料，不同工作区之间默认不可见。

### 3.3 用户私有数据

用户私有数据包括：

1. 用户个人上传文件。
2. 临时分析资料。
3. 私有项目附件。
4. 不应被其他用户检索的草稿或内部资料。

用户私有数据只能由上传者本人访问。管理员是否可见应由企业安全策略单独配置，并写入审计日志。

## 4. RAGFlow Dataset 隔离设计

RAGFlow 负责非结构化文档的解析、切片、向量化和检索。为了让检索范围可控，Dataset 不应混在一起，而应按公共、工作区、用户三个层级拆分。

### 4.1 公共 Dataset

建议建立以下公共 Dataset：

| Dataset | 用途 |
| --- | --- |
| `mdr_public_guidelines` | 指导原则文本库 |
| `mdr_public_review_reports` | 审评报告 |
| `mdr_public_common_questions` | 共性问题、交流园地 |
| `mdr_public_clinical_eval` | 临床评价路径推荐 |
| `mdr_public_draft_comments` | 征求意见稿 |
| `mdr_public_regulatory_notices` | 公告、批件发布 |

公共 Dataset 由系统统一维护，普通用户不能直接修改。

### 4.2 工作区 Dataset

工作区共享资料使用以下命名规则：

```text
mdr_workspace_{workspace_id}
```

例如：

```text
mdr_workspace_reg_team
mdr_workspace_quality_team
mdr_workspace_clinical_team
```

工作区成员能检索本工作区 Dataset，不能检索其他工作区 Dataset。

### 4.3 用户私有 Dataset

用户私有资料使用以下命名规则：

```text
mdr_user_{workspace_id}_{user_id}
```

例如：

```text
mdr_user_reg_team_alice
mdr_user_reg_team_bob
```

用户 `alice` 只能检索自己的私有 Dataset，不能检索 `bob` 的私有 Dataset。

### 4.4 Dataset 选择规则

用户提问时，前端只提交问题、会话 ID 和上传文件信息，不提交 RAGFlow dataset_id。

后端根据登录身份计算可访问 Dataset：

```text
可访问 Dataset =
  公共 Dataset
  + 用户所属工作区 Dataset
  + 用户个人私有 Dataset
```

示例：

```text
用户：alice
工作区：reg_team

可检索：
mdr_public_guidelines
mdr_public_review_reports
mdr_public_common_questions
mdr_public_clinical_eval
mdr_workspace_reg_team
mdr_user_reg_team_alice

不可检索：
mdr_workspace_quality_team
mdr_user_reg_team_bob
```

## 5. MySQL 数据库隔离设计

MySQL 负责结构化注册数据、文档元数据、任务记录、表格抽取结果和审计日志。数据库层不建议按用户拆库，而应通过核心字段实现行级隔离。

### 5.1 文档元数据表

```sql
documents
- id
- title
- source_category
- source_site
- source_url
- publish_date
- crawl_time
- local_path
- file_name
- file_type
- file_hash
- content_type
- visibility
- workspace_id
- user_id
- ragflow_dataset_id
- ragflow_document_id
- status
- created_at
- updated_at
```

关键隔离字段：

| 字段 | 说明 |
| --- | --- |
| `visibility` | `public`、`workspace`、`private` |
| `workspace_id` | 数据所属工作区 |
| `user_id` | 私有数据所属用户 |
| `ragflow_dataset_id` | 对应 RAGFlow Dataset |
| `ragflow_document_id` | 对应 RAGFlow 文档 |

### 5.2 Dataset 映射表

```sql
knowledge_datasets
- id
- dataset_name
- dataset_type
- workspace_id
- user_id
- ragflow_dataset_id
- description
- created_at
```

`dataset_type` 建议取值：

```text
public
workspace
private
```

该表用于把业务权限和 RAGFlow 内部 Dataset 绑定起来。后端查询 RAGFlow 之前，必须先查该表计算允许访问的 Dataset。

### 5.3 工作区成员表

建议增加工作区成员表：

```sql
workspace_members
- id
- workspace_id
- user_id
- role
- status
- joined_at
- created_at
```

`role` 可取：

```text
owner
admin
member
viewer
```

该表用于判断用户是否属于某个工作区，以及是否有上传、删除、查看、管理知识库的权限。

### 5.4 用户上传文件表

建议增加上传文件表：

```sql
uploaded_files
- id
- document_id
- workspace_id
- user_id
- original_file_name
- storage_path
- file_hash
- file_size
- upload_status
- parse_status
- created_at
```

上传文件默认按 `private` 处理。用户主动选择共享到工作区时，才可以转为 `workspace`。

### 5.5 任务表

```sql
agent_tasks
- id
- task_id
- workspace_id
- user_id
- task_type
- question
- status
- allowed_dataset_ids_json
- created_at
- updated_at
```

`allowed_dataset_ids_json` 记录任务创建时实际允许检索的 Dataset 范围，方便后续审计和复盘。

### 5.6 引用记录表

```sql
answer_citations
- id
- task_id
- answer_id
- citation_index
- source_type
- document_id
- chunk_id
- table_id
- table_row_id
- source_url
- quote_text
- page_no
- section_title
- similarity_score
- created_at
```

引用记录不只用于展示来源，也用于证明系统回答没有越权引用其他用户或其他工作区的数据。

## 6. 权限判断规则

后端查询文档时，应统一使用以下权限条件：

```sql
WHERE
  visibility = 'public'
  OR (
    visibility = 'workspace'
    AND workspace_id IN (:user_workspace_ids)
  )
  OR (
    visibility = 'private'
    AND user_id = :current_user_id
  )
```

结构化表格不应绕过 `documents` 表直接查。建议通过 `document_id` 反查权限：

```sql
SELECT r.*
FROM structured_table_rows r
JOIN structured_tables t ON r.table_id = t.id
JOIN documents d ON t.document_id = d.id
WHERE
  d.visibility = 'public'
  OR (
    d.visibility = 'workspace'
    AND d.workspace_id IN (:user_workspace_ids)
  )
  OR (
    d.visibility = 'private'
    AND d.user_id = :current_user_id
  )
```

这样可以保证从表格行、文档、RAGFlow 引用到原始文件，权限逻辑保持一致。

## 7. 后端接口隔离设计

外包团队或前端页面只应调用业务 API，不应直接访问 MySQL、RAGFlow 或对象存储。

建议接口如下：

| 接口 | 用途 | 隔离要求 |
| --- | --- | --- |
| `POST /api/v1/tasks/qa` | 创建问答任务 | 后端计算可访问 Dataset |
| `GET /api/v1/tasks/{task_id}` | 查询任务状态 | 只能查本人或本工作区任务 |
| `GET /api/v1/tasks/{task_id}/result` | 获取任务结果 | 校验任务归属 |
| `POST /api/v1/documents/upload` | 上传文档 | 默认进入用户私有空间 |
| `GET /api/v1/documents` | 文档列表 | 只返回可见文档 |
| `GET /api/v1/datasets` | 知识库列表 | 只返回可访问 Dataset |
| `GET /api/v1/reports/{report_id}` | 下载报告 | 校验报告归属 |

前端不得传入：

```text
ragflow_dataset_id
mysql_table_name
local_path
storage_path
raw_sql
```

这些字段只能由后端根据权限和业务规则生成。

## 8. 智能体调用隔离设计

DeepAgents 主智能体调用 RAGFlow 或 MySQL 工具时，不能直接使用用户输入中的 Dataset、表名或路径。

推荐调用流程：

```text
用户提问
  -> API 层识别用户身份
  -> 查询用户工作区和角色
  -> 计算 allowed_dataset_ids
  -> 创建任务并写入 agent_tasks
  -> 智能体只接收经过裁剪的检索工具
  -> 工具层再次校验权限
  -> 返回带引用来源的回答
```

工具层需要做到：

1. RAGFlow 检索工具只能访问 `allowed_dataset_ids`。
2. MySQL 查询工具只能执行只读查询。
3. 结构化查询必须自动追加权限条件。
4. 文件读取工具只能读取当前任务允许的上传目录。
5. 报告生成工具只能引用当前任务可访问的数据。

## 9. 对象存储隔离设计

原始文件和生成报告建议存放在对象存储中，路径按工作区和用户分层：

```text
public/
  regulatory/
workspace/{workspace_id}/
  documents/
  reports/
users/{workspace_id}/{user_id}/
  uploads/
  reports/
tasks/{task_id}/
  temporary/
```

对象存储不应给前端永久直连权限。下载文件时应由后端校验权限后生成临时下载链接。

## 10. 审计日志设计

系统需要记录关键操作：

```sql
audit_logs
- id
- user_id
- workspace_id
- action
- target_type
- target_id
- request_id
- ip
- user_agent
- result
- created_at
```

建议记录的操作包括：

1. 登录和退出。
2. 创建问答任务。
3. 上传文档。
4. 删除文档。
5. 修改文档可见性。
6. 查询知识库。
7. 下载报告。
8. 管理员查看私有资料。
9. 权限校验失败。

审计日志用于安全追踪，也用于判断是否发生越权访问。

## 11. 越权风险与控制措施

| 风险 | 说明 | 控制措施 |
| --- | --- | --- |
| 前端伪造 dataset_id | 用户手工传入其他人的 Dataset | 后端忽略前端 dataset_id，自行计算 |
| 智能体生成越权 SQL | 模型生成查询其他用户数据的 SQL | 工具层限制只读并追加权限条件 |
| RAGFlow Dataset 混用 | 多用户文档进入同一个私有 Dataset | 按 public/workspace/private 拆分 Dataset |
| 文件路径泄露 | 前端拿到本地路径或对象存储路径 | 只返回 document_id 和临时下载链接 |
| 引用来源越权 | 回答引用了其他用户文档 | answer_citations 记录并校验 document 权限 |
| 外包团队直连核心服务 | 绕过权限和审计 | 只开放业务 API，不开放数据库和 RAGFlow 内部 API |

## 12. 验收标准

### 12.1 权限隔离验收

| 验收项 | 标准 |
| --- | --- |
| 公共资料访问 | 所有授权用户均可检索公共资料 |
| 工作区隔离 | 用户不能检索其他工作区资料 |
| 私有资料隔离 | 用户不能检索他人私有资料 |
| Dataset 列表 | 前端只能看到可访问 Dataset |
| 文档列表 | 前端只能看到可访问 documents |
| 表格查询 | 结构化查询不能跨工作区或跨用户 |
| 文件下载 | 只能下载有权限的文件 |
| 引用记录 | 回答引用均能反查权限 |

### 12.2 安全验收

| 验收项 | 标准 |
| --- | --- |
| 前端不传内部 ID | 不接受前端传入 RAGFlow 内部 dataset_id |
| SQL 只读 | 工具层禁止 INSERT、UPDATE、DELETE、DROP |
| 审计完整 | 上传、检索、下载、删除均有日志 |
| 临时链接 | 下载链接有过期时间 |
| 管理员操作 | 管理员查看私有资料需要审计 |

## 13. 最终建议

建议本项目采用以下隔离方案：

1. 用 `visibility + workspace_id + user_id` 实现 MySQL 行级隔离。
2. 用 `public / workspace / private` 三类 RAGFlow Dataset 实现知识库隔离。
3. 用 `knowledge_datasets` 表维护业务权限和 RAGFlow Dataset 的映射关系。
4. 用 `documents` 表统一管理文档来源、可见性、RAGFlow 文档 ID 和文件路径。
5. 用 `workspace_members` 表判断用户所属工作区和角色。
6. 用 `agent_tasks.allowed_dataset_ids_json` 固化每次任务的可检索范围。
7. 用 `answer_citations` 记录回答引用，保证答案可追溯、可审计。
8. 所有权限判断在后端完成，前端和外包团队不能直接访问 MySQL、RAGFlow、对象存储和模型密钥。

这套设计可以同时满足公共法规资料共享、企业资料隔离、用户私有资料保护和回答可追溯要求，也方便后续扩展到多企业、多工作区和云端部署场景。
