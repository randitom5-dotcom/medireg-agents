# 医疗器械注册知识库搭建与召回方案报告

## 1. 报告目的

本报告用于说明医疗器械注册知识库如何搭建、如何处理多类型文件、如何设计数据分层与召回策略，以及如何保证智能体回答有据可循。

当前工程面向医疗器械注册知识问答、注册证查询、法规依据检索、审评资料分析和报告生成等场景。由于数据来源包含结构化注册数据、法规文件、指导原则、审评报告、共性问题、公告、用户上传资料等多种类型，知识库不宜简单做成一个“大向量库”，而应采用“结构化数据库 + 文档知识库 + 元数据路由 + 混合召回”的方式建设。

## 2. 总体建设思路

推荐采用分层架构：

```text
用户问题
  ↓
意图识别与路由
  ↓
选择数据源
  ├─ MySQL / RDS：结构化注册数据
  ├─ RAGFlow：法规、指导原则、审评报告、共性问题等非结构化文档
  ├─ 用户私有资料库：上传资料、申报文件、内部材料
  └─ 网络搜索：最新公告、官网核验、有效性核验
  ↓
混合召回
  ├─ 元数据过滤
  ├─ 关键词召回
  ├─ 向量召回
  └─ 重排序
  ↓
证据整理
  ↓
生成回答 / Markdown 报告 / PDF 报告
```

该设计的核心原则是：不同类型的数据进入不同的存储和检索通道，智能体根据问题意图选择必要的数据源，而不是每次对所有库做全量召回。

## 3. 数据分层设计

### 3.1 结构化注册数据

适合进入 MySQL / RDS。

典型数据包括：

- 企业名称
- 产品名称
- 注册证编号
- 管理类别
- 型号规格
- 结构组成
- 适用范围
- 批准日期
- 有效期
- 注册人住所
- 生产地址
- 原始 URL
- 本地文件路径

适用问题：

- 查询某企业有哪些注册产品
- 查询某注册证编号对应的产品信息
- 查询某类产品的注册证分布
- 按企业、产品、关键词、管理类别做筛选统计

这类数据不建议主要依赖向量检索，因为字段明确、条件查询强，结构化 SQL 查询更稳定、更可控。

### 3.2 法规与规范性文件

适合进入 RAGFlow / 向量知识库，同时保留法规元数据索引。

典型数据包括：

- 法规
- 部门规章
- 规范性文件
- 公告
- 通告
- 分类目录
- 临床评价相关要求

召回时应重点保留：

- 发布机构
- 发布日期
- 实施日期
- 是否现行有效
- 条款号
- 原始 URL
- 文件标题
- 章节路径

适用问题：

- 某事项的法规依据是什么
- 某要求出自哪份文件
- 某文件是否现行有效
- 注册路径、临床评价、变更注册的规则解释

### 3.3 指导原则与审评文件

适合进入 RAGFlow。

典型数据包括：

- 技术审查指导原则
- 临床评价指导原则
- 产品注册审查指导原则
- 审评报告
- 审评关注点
- 共性问题
- 交流园地内容

适用问题：

- 某类产品注册资料准备要点
- 临床评价路径如何判断
- 审评关注点有哪些
- 同品种比对需要关注哪些资料
- 某类材料产品的风险点

### 3.4 用户上传资料

应进入独立的用户私有资料库或会话工作区，不能与公共知识库混在一起。

典型数据包括：

- 产品技术要求
- 说明书
- 检测报告
- 临床评价资料
- 同品种比对资料
- 企业内部申报材料

要求：

- 按用户、工作区、会话隔离
- 仅当前用户或授权工作区可检索
- 回答中明确区分“公共法规依据”和“用户上传资料依据”

## 4. 文件预处理方案

### 4.1 文件类型处理

不同文件应采用不同预处理方式：

| 文件类型 | 处理方式 | 入库目标 |
| --- | --- | --- |
| JSON | 字段解析、结构化抽取、URL 与文件路径绑定 | MySQL / 元数据表 |
| CSV / XLSX / XLS | 表格清洗、字段标准化、去重 | MySQL |
| PDF | 文本提取，必要时 OCR，按页码保留位置 | RAGFlow |
| DOCX | 提取标题层级、段落、表格 | RAGFlow |
| DOC | 优先转换为 DOCX 或 PDF 后处理 | RAGFlow |
| TXT / MD | 清洗正文、保留标题结构 | RAGFlow |
| ZIP / RAR | 解压后递归识别内部文件 | 按内部文件类型处理 |

### 4.2 文本清洗

预处理阶段建议完成：

- 删除无意义页眉页脚
- 统一空格、换行和乱码字符
- 识别标题层级
- 识别表格与正文
- 保留条款号、页码、章节标题
- 绑定原始 URL
- 绑定本地文件路径
- 计算文件 hash，支持重复检测

### 4.3 切分策略

不同文件不应统一按固定长度切分。

推荐策略：

| 数据类型 | 切分方式 |
| --- | --- |
| 法规文件 | 按章、节、条、款切分，保留条款号 |
| 指导原则 | 按标题层级切分，保留章节路径 |
| 审评报告 | 按产品信息、审评关注点、临床评价、风险收益等模块切分 |
| 共性问题 | 按 Q/A 对切分 |
| 公告正文 | 按公告标题、事项、附件说明切分 |
| 注册 JSON | 不作为主要向量文本，优先结构化入库 |

## 5. 元数据设计

元数据是召回质量的关键。每个文档和 chunk 都应带结构化 metadata。

推荐字段：

```json
{
  "doc_id": "唯一文档ID",
  "chunk_id": "文档片段ID",
  "title": "文件标题",
  "source_type": "法规 / 指导原则 / 审评报告 / 注册证 / 共性问题 / 用户上传",
  "category": "临床评价 / 注册申报 / 产品技术要求 / 分类界定 / 变更注册",
  "product_category": "无源 / 有源 / 植入 / 医美 / 体外诊断",
  "device_keywords": ["胶原", "透明质酸", "重组胶原蛋白"],
  "publish_org": "NMPA / CMDE / 省局",
  "publish_date": "2024-01-01",
  "effective_status": "现行 / 废止 / 未知",
  "source_url": "原始链接",
  "file_path": "本地文件路径",
  "page": 12,
  "section_path": "章节路径",
  "article_no": "条款号",
  "workspace_id": "工作区ID",
  "user_id": "用户ID"
}
```

其中 `source_type`、`category`、`device_keywords`、`effective_status`、`workspace_id`、`user_id` 是召回路由和权限隔离的关键字段。

## 6. 召回策略设计

### 6.1 召回不是每次全库搜索

正确流程应为：

```text
用户问题
  ↓
问题意图识别
  ↓
选择知识源
  ↓
按 metadata 过滤
  ↓
关键词召回 + 向量召回
  ↓
重排序
  ↓
证据合并
```

不建议：

```text
用户问一句
  → MySQL、RAGFlow、网络搜索全部查一遍
```

这样成本高、速度慢、噪声大，也更容易引入错误来源。

### 6.2 意图路由规则

建议路由规则如下：

| 用户问题类型 | 优先数据源 | 是否联网 |
| --- | --- | --- |
| 查询企业、注册证、产品、型号 | MySQL / RDS | 默认不联网 |
| 查询法规依据、指导原则、审评关注点 | RAGFlow | 默认不联网 |
| 查询最新公告、官网状态、是否废止 | 网络搜索 + 官网索引 | 需要联网 |
| 分析上传资料 | 用户私有资料库 | 默认不联网 |
| 生成报告 | 先召回证据，再生成报告 | 视任务需要 |
| 本地无结果或需核验有效性 | 本地库 + 网络搜索补充 | 可联网 |

### 6.3 混合召回方式

建议使用三路召回：

1. **元数据过滤**
   根据产品类型、资料类型、发布日期、机构、有效性、用户权限先缩小范围。

2. **关键词召回**
   适合注册证编号、企业名称、产品名称、条款号、法规标题等精确词。

3. **向量召回**
   适合开放式问题、语义相近问题、审评关注点和经验类问答。

最后进行重排序，优先级建议为：

```text
精确字段命中 > 标题命中 > 条款命中 > 语义相似 > 普通正文命中
```

## 7. 典型场景示例

### 7.1 查询企业注册产品

问题：

```text
南京鼎世医疗器械有限公司有哪些注册产品？
```

路由：

```text
企业名称查询
  → MySQL 注册数据
  → 按企业名称精确/模糊匹配
  → 返回产品名称、注册证编号、有效期、适用范围、原始 URL
```

### 7.2 临床评价路径判断

问题：

```text
重组胶原蛋白产品临床评价路径怎么判断？
```

路由：

```text
产品关键词：重组胶原蛋白
问题意图：临床评价路径
资料类型：法规 + 指导原则 + 审评报告 + 共性问题
  → RAGFlow metadata 过滤
  → 向量召回
  → 关键词召回
  → 重排序
  → 输出判断步骤和依据
```

### 7.3 生成 Markdown 报告

问题：

```text
生成一份《医疗器械临床评价路径判断要点》的 Markdown 报告。
```

路由：

```text
报告生成任务
  → 先召回法规依据和指导原则
  → 补充审评报告或共性问题
  → 整理适用场景、判断步骤、资料清单、风险提示
  → 调用 Markdown 生成工具
```

## 8. 回答可追溯设计

每条回答应尽量包含：

- 结论
- 依据摘要
- 来源文件名称
- 来源类型
- 原始 URL
- 页码 / 条款号 / 章节路径
- 适用边界
- 未检索到或不确定的内容

推荐回答格式：

```text
结论：
...

依据：
1. 《xxx 指导原则》第 x 条 / 第 x 章
2. 《xxx 公告》原始 URL：...
3. 注册数据表：企业 xxx，注册证编号 xxx

风险提示：
- 当前结论基于已入库资料。
- 如涉及法规有效性，应以 NMPA / CMDE 官网最新发布为准。
```

## 9. 权限与隔离要求

知识库应区分公共数据和私有数据。

公共数据：

- 法规
- 指导原则
- 公告
- 审评报告
- 注册公开信息

私有数据：

- 用户上传资料
- 企业申报材料
- 内部分析报告
- 会话历史
- 任务输出文件

隔离建议：

- MySQL 表中保留 `workspace_id`、`user_id`
- RAGFlow dataset 或文档 metadata 中保留工作区字段
- 用户上传资料进入私有工作区
- 召回前先做权限过滤
- 回答中不要跨用户引用资料

## 10. 当前工程落地建议

结合当前 MediReg Agents 工程，建议按以下顺序落地：

1. **先完成数据预处理标准化**
   统一文件清洗、URL 绑定、hash 去重、metadata 抽取。

2. **注册数据入 MySQL**
   JSON / Excel 中的注册证、企业、产品字段进入结构化表。

3. **法规与文档进入 RAGFlow**
   指导原则、审评报告、公告、共性问题按 source_type 分 dataset 或 metadata。

4. **完善提示词路由**
   明确 MySQL、RAGFlow、网络搜索的使用边界，避免每次都联网。

5. **增加召回日志**
   记录每次问题选择了哪些库、召回了哪些 chunk、引用了哪些来源。

6. **完善报告生成**
   报告必须基于已召回证据生成，不能在没有依据时直接编写结论。

## 11. 风险与优化方向

| 风险 | 说明 | 优化方式 |
| --- | --- | --- |
| 文档类型混杂 | 法规、指导原则、审评报告语义不同 | 分 source_type 建库或过滤 |
| 向量召回误命中 | 相似文本不一定适用当前产品 | 增加 metadata 过滤和重排序 |
| 法规有效性不确定 | 本地库可能不是最新 | 对“最新/有效性”问题联网核验 |
| 注册数据不适合语义召回 | 企业、注册证编号需要精确查询 | 使用 MySQL |
| 用户资料泄露 | 私有资料可能被公共召回 | workspace/user 级隔离 |
| 回答不可追溯 | 用户无法判断依据 | 强制返回来源、URL、页码、条款 |

## 12. 结论

医疗器械注册知识库应采用分层建库方式：

```text
MySQL 结构化注册库
+ RAGFlow 法规/指导原则/审评报告知识库
+ 用户私有资料库
+ 官网/联网核验
+ 元数据路由
+ 混合召回
+ 引用溯源
```

这种方式可以同时支持注册证查询、法规依据问答、临床评价路径判断、审评关注点分析和报告生成，并能降低幻觉风险，提高回答的可解释性和可追溯性。
