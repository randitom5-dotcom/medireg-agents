# MediReg Agents 医疗器械注册知识库问答助手可行性分析报告

## 1. 项目名称

项目名称建议定为：

**MediReg  医疗器械注册知识库问答助手**

简称：

**MediReg Agents**

面向医疗器械注册、法规审评、申报资料和企业注册经验的知识检索与智能分析。

## 2. 方案结论

建设一个以 **FastAPI 业务编排层 + DeepAgents 多智能体 + RAGFlow 知识库检索 + MySQL 结构化数据 + React 前端** 为核心的医疗器械注册知识库问答系统。

系统不应只做一个简单聊天机器人，而应定位为“医疗器械注册业务助手”。它需要支持法规问答、申报资料检索、注册证信息查询、指导原则解读、补正问题分析、资料清单生成、注册策略分析和报告输出。

推荐采用分阶段落地：

1. 第一阶段完成可演示闭环：能提问、能检索、能查数据库、能生成报告。
2. 第二阶段完成知识库治理：能上传资料、解析文档、管理元数据、引用来源。
3. 第三阶段完成云端部署和内部试点：支持多用户访问、权限控制、审计日志和并发任务。
4. 第四阶段进入生产化：完善监控、容灾、安全、测试集和持续更新机制。

## 3. 建设目标

MediReg Agents 注册知识库的建设目标如下：

1. 支持医疗器械注册法规、指导原则、审评要点、注册申报资料、临床评价、检验报告、说明书、风险管理、变更注册等内容问答。
2. 支持从企业知识库中检索相关资料，并在回答中给出文档来源、页码、章节、片段和引用依据。
3. 支持查询结构化注册数据，例如产品清单、注册证信息、分类目录、适用标准、申报进度、补正问题、审评状态等。
4. 支持上传 PDF、Word、图片扫描件等文件，并完成解析、切片、索引和检索。
5. 支持生成注册策略分析、法规差异分析、申报资料清单、补正问题汇总等 Markdown/PDF 报告。
6. 支持任务状态追踪，用户能看到智能体执行进度、工具调用和生成结果。
7. 支持基础合规能力，包括敏感信息检测、输入输出审查、操作日志和审计追踪。
8. 支持云端部署，满足多用户访问、并发问答、文档处理和系统监控要求。

## 4. 总体架构

推荐系统架构如下：

```text
用户浏览器
  |
  v
React 前端
  |
  | 问答 / 文件上传 / 报告下载 / 任务状态 / 引用查看
  v
API 网关或负载均衡
  |
  v
FastAPI 业务编排层
  |
  |-- 用户会话
  |-- 任务管理
  |-- WebSocket 状态推送
  |-- 文件上传处理
  |-- 敏感信息检测
  |-- 元数据管理
  |-- 审计日志
  |-- 智能体调度
  |
  |---> DeepAgents 主智能体
  |       |-- 注册数据查询智能体
  |       |-- 知识库检索智能体
  |       |-- 网络搜索智能体
  |       |-- 报告生成工具
  |
  |---> MySQL / RDS
  |       |-- 产品注册数据
  |       |-- 注册证数据
  |       |-- 法规标准索引
  |       |-- 申报任务数据
  |       |-- 文档元数据
  |       |-- 任务与审计日志
  |
  |---> Redis
  |       |-- 会话缓存
  |       |-- 任务队列
  |       |-- 限流计数
  |
  |---> RAGFlow
  |       |-- 文档解析
  |       |-- OCR
  |       |-- 切片
  |       |-- 向量检索
  |       |-- 重排
  |
  |---> 对象存储
  |       |-- 原始上传文件
  |       |-- 生成报告
  |       |-- 临时导出文件
  |
  |---> Tavily / 公开数据源
          |-- 药监公告
          |-- 指导原则
          |-- 公开审评资料
```

这个架构的核心原则是：

1. **结构化注册数据走数据库**，保证查询准确。
2. **非结构化法规和申报文档走 RAGFlow**，保证文档解析和检索质量。
3. **复杂问题由 DeepAgents 编排**，让系统能综合调用多个工具。
4. **业务安全、任务状态和审计由 FastAPI 控制**，避免把业务治理交给大模型。
5. **云端部署采用容器化和可扩展架构**，为多用户访问和后续生产化留空间。

## 5. 核心模块设计

### 5.1 前端模块

前端建议继续使用 React + Vite，重点建设五个页面：

1. 智能问答页：用户输入注册相关问题，查看回答、引用来源和生成文件。
2. 文档管理页：上传法规、指导原则、申报资料、审评意见、检验报告等文件，查看解析状态并管理文档类型。
3. 报告生成页：输入主题后生成注册策略、法规梳理、资料清单、差距分析等报告。
4. 任务监控页：展示智能体执行状态、工具调用、错误信息和任务耗时。
5. 管理后台页：管理用户、知识库、文档类型、审计日志和系统配置。

这样做的理由：

医疗器械注册知识库不是单纯问答工具。注册工作涉及法规依据、产品分类、技术要求、检测标准、临床评价、申报资料和审评反馈，用户需要明确知道系统依据了哪些文件、查询了哪些数据、结论来自哪里。把问答、文档、报告、监控和管理拆成清晰页面，可以提升可用性，也便于后续做权限和审计。

### 5.2 FastAPI 业务编排层

FastAPI 后端建议作为系统中枢，承担以下职责：

1. 接收用户问题和上传文件。
2. 管理任务生命周期。
3. 通过 WebSocket 推送执行进度。
4. 调用智能体、数据库、RAGFlow 和网络搜索工具。
5. 对上传内容进行敏感信息检测。
6. 记录文档元数据、任务状态和审计日志。
7. 统一处理错误、超时、取消和结果下载。
8. 对外提供统一 API，方便后续接入 Dify、企业门户或内部系统。

这样做的理由：

RAGFlow 擅长文档解析和检索，但不适合作为业务系统的总控层；智能体擅长推理和工具选择，但不适合直接管理文件、权限、日志和任务状态。FastAPI 位于前端、智能体、数据库和 RAGFlow 之间，最适合承接业务编排职责。这样可以把业务规则和 AI 能力分开，系统更稳定，也更容易维护。

### 5.3 DeepAgents 多智能体层

建议保留 DeepAgents 作为智能体核心，采用主智能体加子智能体的方式。

| 智能体       | 职责                             |
| --------- | ------------------------------ |
| 主智能体      | 理解用户任务、拆解问题、选择工具、汇总结果          |
| 注册数据查询智能体 | 查询产品、注册证、分类、标准、申报进度等结构化数据      |
| 知识库检索智能体  | 调用 RAGFlow 检索法规、指导原则、申报文件和审评资料 |
| 网络搜索智能体   | 搜索药监公告、指导原则、公开审评资料等外部信息        |
| 报告生成工具    | 将分析结果输出为 Markdown 或 PDF        |

这样做的理由：

医疗器械注册问题通常不是单一检索问题。例如用户可能会问：“某类二类器械首次注册需要准备哪些资料，适用哪些强制性标准，是否需要临床评价，历史补正问题主要集中在哪里？”这类问题需要同时查法规、查指导原则、查企业历史资料、查结构化注册数据，并综合生成结论。多智能体架构比单一 RAG 问答更适合这种复合任务。

### 5.4 RAGFlow 知识库层

RAGFlow 建议专注承担非结构化文档处理：

1. 法规文件、指导原则、审评报告、注册申报资料、检验报告、说明书等文档解析。
2. PDF、Word、扫描件的 OCR 和版面识别。
3. 表格、章节、条款和段落切片。
4. 向量索引。
5. 知识库检索。
6. 检索结果重排。
7. 返回文档名、页码、章节、片段和相似度。

这样做的理由：

医疗器械注册资料中会有大量法规 PDF、指导原则、标准清单、审评意见、申报资料模板、扫描件和表格。自研文档解析成本高、效果不稳定，而 RAGFlow 的优势正是在复杂文档解析、切片和检索。让 RAGFlow 做它擅长的事情，可以减少重复开发，也能提升知识库检索质量。

### 5.5 MySQL 结构化数据层

结构化数据建议继续使用 MySQL 管理，例如：

1. 产品基础信息。
2. 医疗器械分类编码。
3. 注册证信息。
4. 适用法规和标准索引。
5. 申报项目和审评进度。
6. 补正问题和整改记录。
7. 文档元数据。
8. 任务状态和审计日志。

这样做的理由：

结构化注册数据不适合全部放进向量库。产品分类、注册证编号、适用标准、申报状态、补正次数、审评节点等数据需要精确查询、聚合统计和条件过滤，数据库比 RAG 更可靠。RAGFlow 负责文档证据，MySQL 负责准确数据，两者分工清晰，系统回答会更可信。

## 6. 业务流程设计

### 6.1 问答流程

```text
用户提问
  |
  v
FastAPI 创建任务
  |
  v
输入安全检查
  |
  v
主智能体分析问题
  |
  |-- 需要结构化注册数据 -> 查询 MySQL
  |-- 需要法规或申报文件依据 -> 检索 RAGFlow
  |-- 需要外部公开信息 -> 调用 Tavily
  |
  v
证据汇总与冲突检查
  |
  v
生成回答或报告
  |
  v
输出安全检查
  |
  v
返回答案、引用来源和文件下载链接
```

这样做的理由：

这个流程避免了单纯依赖大模型直接回答。每个重要结论都尽量来自数据库、知识库或公开资料，智能体主要负责组织证据和生成表达。这样可以降低幻觉风险，并让回答具备可追溯性。

### 6.2 文档入库流程

```text
用户上传文档
  |
  v
文件基础校验
  |
  v
敏感信息检测
  |
  v
文档类型识别
  |
  v
登记文档元数据
  |
  v
上传到对象存储
  |
  v
上传到 RAGFlow
  |
  v
RAGFlow 解析、切片、索引
  |
  v
后端轮询或接收状态
  |
  v
前端展示处理结果
```

这样做的理由：

企业知识库不能只做“上传即入库”。上传前需要判断是否包含敏感信息，上传后需要知道文件属于什么类型、归属哪个知识库、解析是否成功、后续能否检索。把文档入库做成可追踪流程，才能支撑真实注册业务使用。

## 7. 云端部署方案

### 7.1 推荐部署方式

建议采用容器化部署。初期可以使用云服务器加 Docker Compose，正式试点和生产建议使用 Kubernetes 或云厂商容器服务。

推荐演进路线：

| 阶段     | 部署方式                                   | 适用场景               |
| ------ | -------------------------------------- | ------------------ |
| PoC 阶段 | 单台云服务器 + Docker Compose                | 5-20 人试用，验证功能闭环    |
| 内部试点   | 多台云服务器 + Docker Compose 或轻量 Kubernetes | 20-100 人使用，开始关注稳定性 |
| 生产阶段   | Kubernetes + 托管数据库 + 对象存储 + 监控告警       | 多部门使用，需要扩容、审计和容灾   |

### 7.2 云端组件规划

推荐云端组件如下：

| 组件      | 推荐方案                      | 说明                     |
| ------- | ------------------------- | ---------------------- |
| 前端      | Nginx + CDN 或对象存储静态站点     | React 构建产物静态部署         |
| API 服务  | FastAPI 容器，多副本部署          | 承接业务接口、任务调度和 WebSocket |
| RAGFlow | 独立容器或独立节点部署               | 负责文档解析、向量检索和重排         |
| MySQL   | 云数据库 RDS MySQL            | 存储结构化注册数据、任务和审计        |
| Redis   | 云 Redis 或自建 Redis         | 缓存、队列、限流、任务状态          |
| 对象存储    | OSS/COS/S3/MinIO          | 存储上传原文档和生成报告           |
| 向量与检索存储 | RAGFlow 内置 ES/Infinity    | 保持 RAGFlow 原生检索能力      |
| 日志监控    | Prometheus + Grafana 或云监控 | 监控服务、接口、资源和错误          |
| 密钥管理    | 云密钥管理 KMS 或环境变量注入         | 管理 API Key、数据库密码等敏感配置  |

### 7.3 推荐生产部署拓扑

```text
公网用户
  |
  v
HTTPS 负载均衡 / API 网关
  |
  |---> 前端静态资源 CDN
  |
  |---> FastAPI 服务副本 1
  |---> FastAPI 服务副本 2
  |---> FastAPI 服务副本 N
          |
          |---> Redis
          |---> RDS MySQL
          |---> 对象存储
          |---> RAGFlow 服务
                    |
                    |---> RAGFlow MySQL
                    |---> RAGFlow Redis
                    |---> RAGFlow MinIO 或对象存储
                    |---> RAGFlow ES/Infinity
```

### 7.4 云服务器规格建议

PoC 阶段：

| 服务          | 建议规格                                     |
| ----------- | ---------------------------------------- |
| 应用服务器       | 4 核 8G，100G 磁盘                           |
| RAGFlow 服务器 | 8 核 32G，200G 磁盘                          |
| GPU         | 如需要本地 OCR/Embedding/重排，可选 1 张 16G 显存 GPU |
| 数据库         | 可先 Docker 内置，建议尽早迁移到 RDS                 |

内部试点阶段：

| 服务      | 建议规格               |
| ------- | ------------------ |
| FastAPI | 2 个副本，每个 4 核 8G    |
| RAGFlow | 1-2 个节点，每个 8 核 32G |
| MySQL   | RDS 2 核 8G 起步      |
| Redis   | 2G-4G 起步           |
| 对象存储    | 按文档量计费             |

生产阶段：

| 服务      | 建议规格                  |
| ------- | --------------------- |
| FastAPI | 3 个以上副本，支持水平扩容        |
| RAGFlow | 独立节点，按文档处理量和检索 QPS 扩容 |
| MySQL   | RDS 高可用版，开启备份         |
| Redis   | 主从或集群版                |
| 对象存储    | 开启版本控制、生命周期和权限策略      |
| 监控      | 接入云监控、日志服务和告警         |

### 7.5 为什么这样部署

这样部署的原因有三点：

1. **前后端分离便于扩容**：前端静态化，后端容器化，接口压力增加时只需要扩 FastAPI 副本。
2. **RAGFlow 独立部署便于资源隔离**：文档解析、OCR 和检索比较消耗 CPU、内存和磁盘，把它和业务 API 分开，可以避免互相拖垮。
3. **数据库和对象存储托管化更稳**：注册资料和审计日志是核心资产，使用 RDS 和对象存储比自建更适合备份、恢复和权限管理。

## 8. 并发与容量设计

### 8.1 用户并发分层

建议按三个阶段设计并发能力：

| 阶段   | 用户规模      | 同时在线     | 并发问答      | 并发文档解析   |
| ---- | --------- | -------- | --------- | -------- |
| PoC  | 5-20 人    | 5 人以内    | 1-3 个任务   | 1 个任务    |
| 内部试点 | 20-100 人  | 10-30 人  | 5-10 个任务  | 2-3 个任务  |
| 生产初期 | 100-500 人 | 30-100 人 | 20-50 个任务 | 5-10 个任务 |

这里的“并发问答”不是普通接口 QPS，而是指同时运行的智能体任务。因为一次问答可能包含 LLM 调用、RAG 检索、数据库查询和报告生成，资源消耗远高于普通 REST 请求。

### 8.2 并发控制策略

建议采用以下控制策略：

1. FastAPI 普通接口保持同步响应，长任务进入后台任务队列。
2. 智能体问答、报告生成、文档解析统一进入任务队列。
3. Redis 记录任务状态、队列状态和用户限流计数。
4. WebSocket 只负责状态推送，不直接承载重计算。
5. 每个用户限制同时运行任务数，例如普通用户 1-2 个，管理员 3-5 个。
6. 系统设置全局并发上限，超过上限进入排队。
7. LLM 调用设置超时、重试和失败降级。
8. 文档解析任务与问答任务分队列，避免大文件解析阻塞问答。

推荐队列划分：

| 队列             | 用途                | 并发建议                |
| -------------- | ----------------- | ------------------- |
| `qa_queue`     | 问答和智能体分析          | 按 LLM 额度和 API 副本数配置 |
| `ingest_queue` | 文档上传、解析、入库        | 按 RAGFlow 处理能力配置    |
| `report_queue` | Markdown/PDF 报告生成 | 独立限流，避免占用问答资源       |
| `sync_queue`   | 外部法规数据同步          | 低优先级，定时执行           |

### 8.3 后端扩容方式

FastAPI 服务应设计为无状态服务，用户会话、任务状态和缓存放到 Redis 或数据库中。

扩容方式：

1. 增加 FastAPI 容器副本，提高 API 接入能力。
2. 增加任务 Worker 副本，提高智能体任务处理能力。
3. 增加 RAGFlow 节点或提高 RAGFlow 资源，提高检索和解析能力。
4. 对 MySQL 增加连接池、索引和只读副本。
5. 对对象存储使用直传或分片上传，减少 API 服务带宽压力。

### 8.4 数据库连接池建议

建议配置连接池：

| 环境   | FastAPI 副本数 | 每副本连接池 | MySQL 最大连接数建议 |
| ---- | ----------- | ------ | ------------- |
| PoC  | 1           | 5-10   | 50            |
| 内部试点 | 2           | 10-20  | 100-200       |
| 生产初期 | 3-5         | 20-30  | 300-500       |

数据库查询工具必须限制只读 SQL，并为复杂查询设置超时，避免智能体生成大范围扫描语句拖慢数据库。

### 8.5 LLM 调用并发

LLM 是系统并发的核心瓶颈之一。建议：

1. 根据模型供应商的 RPM、TPM、并发数限制设置全局限流。
2. 对每个用户设置请求频率限制。
3. 对长报告生成任务使用后台队列。
4. 对常见法规问答结果做缓存。
5. 对失败调用进行有限重试，不做无限重试。
6. 对不同任务设置不同模型，例如普通问答用较快模型，复杂报告用能力更强模型。

### 8.6 RAGFlow 并发

RAGFlow 的压力主要来自两个方面：

1. 文档解析：CPU、内存、OCR 和磁盘压力较大。
2. 在线检索：对 ES/Infinity、向量检索和重排有压力。

建议：

1. 文档解析任务限流，避免多人同时上传大文件导致系统拥塞。
2. 大文件上传后异步处理，前端显示排队和解析状态。
3. 在线问答检索设置 `top_k` 和相似度阈值，避免过度召回。
4. 热门法规和指导原则检索结果可以缓存。
5. RAGFlow 与业务 API 分离部署，必要时独立扩容。

## 9. 安全与合规设计

建议至少实现以下安全措施：

1. 数据库工具只允许只读 SQL，例如 `SELECT`、`SHOW`、`DESCRIBE`、`EXPLAIN`。
2. 上传文件前进行敏感信息检测。
3. 对身份证号、手机号、银行卡号、患者信息、临床试验受试者信息、商业秘密等进行拦截或脱敏。
4. 对用户输入进行 Prompt Injection 检测。
5. 输出结果增加合规提示，避免生成未经确认的监管结论、医疗建议、夸大性产品表述或替代正式注册判断。
6. 所有任务记录审计日志，包括用户问题、工具调用、引用资料、生成文件和异常信息。
7. 后续增加用户、角色、工作区和知识库权限隔离。
8. 云端部署必须使用 HTTPS，数据库和对象存储不直接暴露公网。
9. API Key、数据库密码、模型密钥统一通过环境变量或云密钥管理服务注入。

这样做的理由：

医疗器械注册领域涉及监管判断、技术资料、临床资料和企业商业秘密。如果没有审计日志、敏感信息检测和输出约束，系统很难进入真实业务环境。安全能力越早加入，后续改造成本越低。

## 10. 数据库设计建议

在现有示例数据基础上，建议逐步调整为医疗器械注册场景的数据模型，并新增以下业务表：

| 表名                          | 用途                               |
| --------------------------- | -------------------------------- |
| `device_products`           | 记录医疗器械产品基础信息                     |
| `registration_certificates` | 记录注册证、备案凭证、有效期和变更情况              |
| `device_classifications`    | 记录分类目录、管理类别和分类编码                 |
| `applicable_standards`      | 记录产品适用标准、强制性标准和推荐性标准             |
| `submission_projects`       | 记录注册申报项目、负责人、节点和状态               |
| `deficiency_items`          | 记录补正问题、整改措施和关闭状态                 |
| `documents`                 | 记录上传文档的文件名、类型、来源、状态、所属知识库        |
| `knowledge_datasets`        | 记录本地业务知识库与 RAGFlow dataset 的映射关系 |
| `agent_tasks`               | 记录每次智能体任务的状态、开始时间、结束时间和结果        |
| `audit_logs`                | 记录用户操作、工具调用、异常和输出文件              |
| `pii_scan_logs`             | 记录敏感信息检测结果                       |
| `source_registry`           | 记录外部数据源、监管站点和爬虫来源                |

这样做的理由：

这些表不是为了多建表，而是为了让系统从 Demo 变成可管理的平台。没有产品和注册证表，就无法做精确注册数据查询；没有文档表，就不知道知识库里有什么；没有任务表，就无法追踪执行过程；没有审计表，就无法解释系统为什么这样回答；没有敏感信息记录，就很难做合规闭环。

## 11. 测试方案

### 11.1 测试目标

测试不只验证系统能不能跑，还要验证它是否适合医疗器械注册业务使用。

测试目标包括：

1. 功能正确：问答、上传、检索、报告、下载、状态推送都可用。
2. 检索可信：回答能够引用正确来源。
3. 数据准确：结构化查询结果与数据库一致。
4. 性能稳定：多用户并发下系统不崩溃。
5. 安全可控：敏感信息、危险 SQL、越权访问能被拦截。
6. 可运维：日志、监控、告警和错误追踪可用。

### 11.2 功能测试

功能测试范围：

| 模块    | 测试内容                        |
| ----- | --------------------------- |
| 用户问答  | 普通问答、复杂问答、追问、无答案场景          |
| 数据库查询 | 产品查询、注册证查询、分类查询、标准查询、申报进度查询 |
| 知识库检索 | 法规检索、指导原则检索、企业资料检索、引用展示     |
| 文档上传  | PDF、Word、扫描件、大文件、重复文件、错误格式  |
| 报告生成  | Markdown 生成、PDF 转换、文件下载     |
| 任务状态  | WebSocket 连接、任务进度、取消任务、失败提示 |
| 管理后台  | 文档列表、任务列表、审计日志、用户权限         |

### 11.3 RAG 检索质量测试

建议建立医疗器械注册标准测试集，至少包含 100-200 个问题。

测试集类型：

1. 法规条款类：例如某类产品注册适用哪个法规或指导原则。
2. 资料清单类：例如首次注册、延续注册、变更注册需要哪些资料。
3. 判断类：例如某场景是否需要临床评价。
4. 对比类：例如不同注册路径或不同指导原则的差异。
5. 溯源类：要求回答必须给出文档来源和页码。
6. 无答案类：知识库没有依据时，系统必须说明无法确认。

核心指标：

| 指标     | 建议目标                   |
| ------ | ---------------------- |
| 引用准确率  | 试点阶段不低于 85%            |
| 答案可用率  | 试点阶段不低于 80%            |
| 幻觉率    | 关键法规问题低于 5%            |
| 无答案识别率 | 不低于 80%                |
| 平均响应时间 | 普通问答 10-30 秒内，复杂报告允许更长 |

### 11.4 数据库与工具调用测试

重点验证：

1. 智能体只能执行只读 SQL。
2. `DELETE`、`UPDATE`、`INSERT`、`DROP`、`ALTER` 等语句必须被拒绝。
3. 大范围查询必须有超时限制。
4. 查询结果与数据库原始数据一致。
5. 工具失败时，智能体能给出清晰错误说明，而不是编造结果。

### 11.5 并发与性能测试

建议分三轮压测：

| 轮次    | 目标         | 示例              |
| ----- | ---------- | --------------- |
| 基础压测  | 验证 API 稳定性 | 20 并发普通接口请求     |
| 智能体压测 | 验证问答任务能力   | 5、10、20 个并发问答任务 |
| 混合压测  | 验证真实使用场景   | 问答、上传、报告生成同时执行  |

需要关注的指标：

1. API 成功率。
2. 平均响应时间和 P95 响应时间。
3. 智能体任务平均耗时。
4. 队列等待时间。
5. RAGFlow 检索耗时。
6. LLM 调用失败率。
7. CPU、内存、磁盘和数据库连接数。

### 11.6 安全测试

安全测试范围：

1. SQL 注入测试。
2. Prompt Injection 测试。
3. 越权访问测试。
4. 敏感信息上传测试。
5. API Key 泄露检查。
6. 文件类型伪造测试。
7. 大文件和压缩包风险测试。
8. 未登录访问和跨用户数据访问测试。

### 11.7 用户验收测试

建议邀请注册、法规、质量、临床评价和技术文档人员参与验收。

验收方式：

1. 每个角色准备 10-20 个真实业务问题。
2. 让系统回答并生成报告。
3. 由业务专家判断答案是否可用、引用是否正确、风险提示是否充分。
4. 将问题、答案、人工评分和改进意见沉淀为测试集。

验收标准：

1. 常见注册问题可以给出有依据回答。
2. 回答能清楚展示引用来源。
3. 无依据问题不会强行编造。
4. 文档上传和解析过程可追踪。
5. 报告格式满足内部使用要求。

4. 重要配置和部署脚本进入 Git 管理，但不得提交密钥。
5. 至少每季度进行一次恢复演练。

## 14. 关键选择理由

### 14.1 为什么使用 FastAPI 做业务编排

因为系统需要管理任务、文件、状态、日志、权限和安全检查，这些都属于后端业务逻辑，不适合交给大模型或 RAGFlow 直接处理。FastAPI 开发效率高、接口清晰、适合异步任务和 WebSocket，适合作为系统中枢。

### 14.2 为什么使用 DeepAgents

因为目标场景不是简单知识库问答，而是多来源信息综合分析。DeepAgents 可以根据问题动态调用数据库、知识库、网络搜索和报告生成工具，更适合复杂注册问题拆解。

### 14.3 为什么使用 RAGFlow

因为医疗器械注册资料中存在大量 PDF、扫描件、表格和复杂版式文档。RAGFlow 在文档解析、切片、OCR、检索和重排方面更专业，可以减少自研成本，并提升知识库质量。

### 14.4 为什么保留 MySQL

因为产品、注册证、分类编码、适用标准、申报进度、补正问题等数据需要精确查询和统计分析。向量检索适合查文档，不适合做严格结构化统计。MySQL 可以保证这类数据查询的准确性。

### 14.5 为什么需要队列和并发控制

因为智能体任务不是普通接口请求，一次任务可能调用多次模型、检索多次知识库、查询数据库并生成文件。如果不做队列和限流，高峰期容易出现模型限流、RAGFlow 阻塞、数据库连接耗尽和用户体验不稳定。

### 14.6 为什么要尽早做安全和审计

因为医疗器械注册领域涉及监管判断、技术资料、临床资料和企业商业秘密。如果没有审计日志、敏感信息检测和输出约束，系统很难进入真实业务环境。安全能力越早加入，后续改造成本越低。

## 15. 风险与应对

| 风险                | 影响         | 应对措施                               |
| ----------------- | ---------- | ---------------------------------- |
| RAGFlow 文档解析效果不稳定 | 检索质量下降     | 建立法规、标准、注册资料、扫描件测试集，评估 OCR、表格和切片效果 |
| 智能体回答产生幻觉         | 影响可信度      | 要求回答必须附证据，无法确认时明确说明                |
| 数据库查询存在误操作风险      | 可能破坏数据     | SQL 工具限制只读语句                       |
| 上传文件包含敏感信息或商业秘密   | 存在合规风险     | 上传前检测，必要时拒绝或脱敏                     |
| 网络搜索内容不可信         | 影响结论质量     | 网络结果只作为补充，并标注来源                    |
| 法规和指导原则更新不及时      | 影响注册判断     | 建立外部数据源登记和定期更新机制                   |
| 并发任务过多            | 系统响应变慢或失败  | 使用队列、限流、任务排队和服务扩容                  |
| 云端部署配置不当          | 数据泄露或服务不稳定 | 使用 VPC、HTTPS、RDS、对象存储权限和密钥管理       |
| 本地服务端口冲突          | 影响部署和调试    | 固定端口规划，区分 RAGFlow、Dify 和项目服务       |

## 16. 最终建议

建议按以下路径推进 MediReg Agents：

1. 继续以 `MediReg Agents` 作为项目底座。
2. 优先完成数据库只读保护、RAGFlow 检索引用、报告生成和前端结果展示。
3. 第二步补齐文件上传、文档元数据、RAGFlow 入库和解析状态追踪。
4. 第三步增加 Redis 队列、任务限流、并发控制和云端部署能力。
5. 第四步增加敏感信息检测、审计日志、权限隔离和知识库治理。
6. 第五步建立医疗器械注册测试集，持续评估回答准确率、引用准确率和系统稳定性。

该方案的优势是：开发成本可控、能复用当前项目、适合快速演示，也保留了向企业级医疗器械注册知识库平台演进的空间。整体路线稳妥，可落地性较强。
